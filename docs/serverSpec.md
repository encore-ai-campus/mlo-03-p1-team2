# 서버 구성과 자원 확인 기준

이 문서는 최신 [networkInfo.md](networkInfo.md)의 서버 역할과 확인된 운영 현황을 기준으로 구성 범위와
확인할 자원을 정리한다. IP·담당자 원본은 해당 문서에서 관리한다.
이 정리는 저장소 문서 기준이며 실제 서버 설정을 변경하거나 새로 실측한 결과가 아니다.
접속·서비스 기동·HAProxy·nginx·TLS 절차는 [FrontToBackSetting.md](FrontToBackSetting.md)를 따른다.

## 서버별 역할

| 구분 | 서버 | 문서상 역할 |
| --- | --- | --- |
| 관계형 DB | `192.168.0.171`~`173` | MariaDB 3대 |
| 행동 로그 DB | `192.168.0.174` | MongoDB |
| 애플리케이션 | `192.168.0.175`·`176` | FastAPI 2대 |
| 웹 | `192.168.0.177`·`178` | Nginx 2대 |
| 프록시 | `192.168.0.179`~`181` | HAProxy 3대 |
| 메트릭 수집 | `192.168.0.187` | Prometheus |
| 대시보드 | `192.168.0.188` | Grafana |
| 로그 조회·저장 | `192.168.0.189` | Loki |

`183`의 Grafana, `184`의 Prometheus, `186`의 Loki는 최신 표에서 삭제된 항목이므로
현재 대상 서버로 사용하지 않는다. `182`·`185`·`190`은 역할이 지정되지 않았다.
운영체제·실행 버전·서비스 기동 여부는 이 IP 목록만으로 확정하지 않는다.

## 요청 경로와 확인되지 않은 구성

연결 가이드에 기록된 웹 요청 경로는 다음과 같다.

```text
브라우저
  → 프런트 HAProxy 181
  → Nginx 177·178
  → 백엔드 HAProxy 179
  → FastAPI 175·176
  → MariaDB 171 / MongoDB 174
```

최신 네트워크 표에는 MariaDB `172`·`173`과 HAProxy `180`도 포함된다.
하지만 이 표에는 MariaDB의 복제 방식·주/보조 역할이나 `180`의 프록시 대상이 적혀 있지 않다.
위 요청 경로에 임의로 추가하거나 DB 복제·자동 장애 전환이 적용됐다고 가정하지 않는다.
실제 연결 설정을 확인하면 연결 가이드에서 갱신한다.

Prometheus는 `192.168.0.187`, Grafana는 `192.168.0.188`, Loki는 `192.168.0.189`의
각각 별도 서버로 운영한다. Alloy는 모든 서버에 설치되어 있다.

## 실제 자원 할당을 확인할 항목

물리 장비는 PC 1·2·3 모두 같은 사양의 일반 PC다.
PC별 서비스 배치는 다음과 같다. Alloy는 아래 모든 서버에 설치되어 있다.

| 장비 | 형태 | RAM | 기존 디스크 산정 기준 | 확인된 배치 |
| --- | --- | ---: | ---: | --- |
| PC 1 | 일반 PC | 32GB | 100GB | FastAPI 175·176, HAProxy 179, Prometheus 187, Grafana 188 |
| PC 2 | 일반 PC | 32GB | 100GB | Nginx 177·178, HAProxy 181, Loki 189 |
| PC 3 | 일반 PC | 32GB | 100GB | MariaDB 171·172·173, MongoDB 174, HAProxy 180 |

100GB는 기존 문서의 디스크 산정 기준이다. 전체 용량인지 VM용 여유 공간인지와
실제 잔여 공간은 별도로 확인한다. 다음 항목은 아직 실제 설정 대조가 필요하다.

| 대상 | 확인할 항목 |
| --- | --- |
| 물리 PC | CPU·가용 디스크·장비별 실제 사용량 |
| 각 VM | vCPU·RAM·디스크 할당, 게스트 OS, 가상화 방식 |
| FastAPI | worker 수, 프로세스별 메모리, DB 연결 풀 |
| MariaDB | 복제·접속 경로, buffer pool, 연결 한도, 데이터·여유 공간 |
| MongoDB | 캐시 설정, 데이터·인덱스 크기, 가용 디스크 |
| Prometheus | scrape 간격·대상, 보관 기간·용량 제한 |
| Alloy | 서버별 수집 대상·전송 경로·서비스 상태 |
| Loki | 수집 경로, 보관·삭제 설정, 저장량 |
| HAProxy·Nginx | 전달 대상, 포트, TLS 종료 위치, 헬스체크 |

서버별 사양을 확인하기 전에는 과거 제안값을 실측 사양으로 옮겨 적지 않는다.
성능 수치는 [loadTestResult.md](loadTestResult.md)의 실행 조건·실측 결과와 함께 해석한다.

## 초기 제안과의 차이

2026-11-05의 자원 배치 제안 중 아래 항목은 최신 네트워크 표의 역할 분리와 다르다.
초기 자원표·설계 근거·제약은 아래 [초기 자원 산정과 설계 근거](#초기-자원-산정과-설계-근거)에 통합했다.

| 초기 제안 | 최신 네트워크 문서 기준 |
| --- | --- |
| Nginx·FastAPI를 `app-vm`에 함께 배치 | Nginx 177·178, FastAPI 175·176으로 역할 분리 |
| MariaDB VM 1대 | MariaDB 171·172·173 기록. 복제·역할은 미확정 |
| PC마다 프록시 1대, 총 3대 | PC 1에 179, PC 2에 181, PC 3에 180 배치 |
| vCPU·RAM·디스크 및 보관 기간을 초기 예산으로 제시 | 실제 할당·설정 확인 필요 |

VM 자원표, FastAPI worker 2개, DB 캐시 설정은
당시 제안값이다. 현재 적용된 값이나 처리 성능을 보장하는 수치로 사용하지 않는다.

## 초기 자원 산정과 설계 근거

2026-11-05에 작성한 ADR-001의 자원 산정 참고값과 설계 근거다.
물리 장비 사양과 DB 배치는 위에서 확인한 내용을 따른다.
모니터링은 서비스별 별도 서버로 운영하고 Alloy는 모든 서버에 설치되어 있다.
아래 VM 자원·애플리케이션 설정의 제안값은 실제 적용값과 구분한다.

| 항목 | 내용 |
|---|---|
| 상태 | 제안됨 |
| 작성일 | 2026-11-05 |
| 적용 범위 | 학습·개발 및 소규모 서비스 환경 |
| 결정 대상 | VM 구성, 서비스 배치, CPU·메모리·디스크 할당 |

### 1. 배경

3대의 PC에서 VMware를 이용해 다음 서비스를 운영하려고 한다.

- Nginx, FastAPI
- MariaDB, MongoDB
- 프록시 서버 3대
- Grafana, Prometheus, Alloy, Loki

제한된 물리 자원 안에서 애플리케이션, 데이터베이스, 모니터링의 부하를 분리하고, 호스트 운영체제의 여유 자원을 확보해야 한다.

#### 하드웨어 및 산정 가정

물리 PC 사양과 DB 배치는 위의 장비 표를 기준으로 한다.

다음 조건을 전제로 한다.

- VM 운영체제는 GUI 없는 Linux를 사용한다.
- 프록시는 일반적인 HTTP/HTTPS 프록시이며, 대용량 캐싱이나 콘텐츠 검사를 수행하지 않는다.
- 대규모 트래픽과 대용량 데이터 처리는 초기 범위에 포함하지 않는다.
- 할당값은 성능을 보장하는 수치가 아닌 초기 운영 예산이다.
- 100GB가 전체 디스크 용량이라면 호스트 OS 사용량을 제외하고 VM별 디스크 예산을 산정한다.

### 2. 배치와 자원 참고값

실제 PC별 서비스 배치는 위 장비 표를 따른다.
PC 1은 FastAPI·메트릭·대시보드, PC 2는 Nginx·로그, PC 3은 DB를 담당하고,
각 PC에 HAProxy를 1대씩 배치했다.

Alloy는 모든 서버에 설치되어 있다. 아래 표는 웹·DB·프록시의 초기 자원 산정값이다.
별도 운영 중인 Prometheus·Grafana·Loki 서버의 실제 자원 할당은 별도로 확인한다.

#### 초기 서비스별 자원 참고값

| 산정 대상 | vCPU | RAM | 디스크 | 적용 범위 |
| --- | ---: | ---: | ---: | --- |
| 웹·애플리케이션 통합 예산 | 4 | 6GB | 25GB | 초기 통합 구성의 참고값. 현재 분리된 FastAPI·Nginx 서버의 할당값은 아님 |
| HAProxy 1대 | 1 | 2GB | 10GB | 프록시별 초기 참고값 |
| MariaDB 1대 | 2 | 8GB | 30GB | DB별 초기 참고값 |
| MongoDB 1대 | 2 | 8GB | 30GB | DB별 초기 참고값 |

RAM과 디스크 할당량에는 게스트 OS 및 Alloy 사용분을 포함한다.
DB 행은 현재 4개 DB 서버에 그대로 적용된 할당표가 아니다.
PC 3의 전체 예산은 MariaDB 3대·MongoDB·HAProxy와 호스트 OS 사용분을 합쳐 실제 설정으로 다시 산정한다.

물리 장비별 자원 합계는 각 서버의 실제 할당을 확인한 뒤 산정한다.
vCPU는 물리 코어를 전용으로 예약한다는 의미가 아니다.

### 3. 설계 근거

| 결정 | 근거 |
|---|---|
| FastAPI는 PC 1, Nginx는 PC 2에 배치 | 웹 정적 파일 제공과 애플리케이션 처리를 물리 장비별로 구분한다. |
| DB별 VM 분리 | 메모리, 설정, 재시작 및 저장 공간을 독립적으로 관리한다. |
| DB 서버를 PC 3에 모아 배치 | MariaDB·MongoDB와 DB 측 HAProxy를 같은 물리 장비에서 운영한다. |
| Prometheus·Grafana·Loki를 각각 별도 서버로 운영 | 서비스별 자원·재시작·장애 영향을 구분한다. |
| 프록시를 장비별로 분산 | 한 PC 중단 시 모든 프록시가 동시에 중단되는 상황을 피한다. |
| Alloy를 모든 서버에 설치 | 서버별 로그·메트릭 수집 설정을 관리한다. |

### 4. 운영 설정 제안

#### 애플리케이션 및 데이터베이스

- Nginx는 외부 요청 수신, TLS 종료 및 FastAPI로의 요청 전달을 담당한다.
- FastAPI는 worker 2개로 시작한다. worker 수를 늘릴 때 프로세스별 메모리 증가를 고려한다.
- MariaDB의 InnoDB buffer pool은 약 4GB로 시작한다.
- MongoDB의 WiredTiger 캐시는 약 3GB로 시작한다.
- DB별 30GB 디스크에는 OS가 포함되므로, 초기 DB 데이터 예산은 각각 약 15~20GB 이내로 계획한다.
- 프록시의 디스크 캐시는 비활성화하거나 작은 크기로 제한한다.

#### 모니터링 및 로그

- Prometheus: `192.168.0.187`에서 메트릭을 수집한다.
- Grafana: `192.168.0.188`에서 대시보드를 제공한다.
- Loki: `192.168.0.189`에서 로그를 저장·조회한다.
- Alloy: 모든 서버에 설치되어 있다.
- 수집 대상·전송 경로, 서버별 메모리·디스크, scrape 간격과 보관·삭제 설정은 실제 설정을 확인해 기록한다.
- 로컬 로그에도 로그 회전을 적용한다.

#### 가상화 및 네트워크

- PC 1·2·3 모두 일반 PC이며 VMware를 사용한다.
- VM은 브리지 네트워크와 고정 IP 또는 DHCP 예약으로 연결한다.
- 물리 PC 간 연결은 유선 1Gbps 이상을 권장한다.
- DB, Prometheus, Loki는 내부망에서 필요한 대상만 접근하도록 제한한다.

### 5. 검토한 대안

| 대안 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| 모든 서비스를 개별 VM으로 분리 | 서비스별 격리 수준이 높음 | 게스트 OS의 메모리·디스크 사용과 관리 부담이 증가함 |
| 모든 서비스를 한 PC에 집중 | 초기 구성이 단순함 | 부하가 집중되고 해당 PC 장애 시 전체 서비스가 중단됨 |
| MariaDB와 MongoDB를 PC별로 분산 | 두 DB의 물리 디스크 부하를 분리할 수 있음 | 초기에는 역할별 구성을 단순하게 유지하고, DB 쓰기 부하 증가 시 재검토함 |

### 6. 결과 및 제약

#### 기대 효과

- 애플리케이션, DB, 모니터링 간 물리 자원 경합을 줄인다.
- 호스트 OS와 개발 도구를 위한 메모리 여유를 확보한다.
- VM별 역할과 자원 사용량을 구분하기 쉽다.
- 프록시 장애 범위를 물리 PC 단위로 분산한다.

#### 수용하는 제약

- PC 1 장애 시 FastAPI 2대·HAProxy 179·Prometheus·Grafana가 영향을 받는다.
- PC 2 장애 시 Nginx 2대·HAProxy 181·Loki가 영향을 받는다.
- PC 3 장애 시 MariaDB 3대·MongoDB·HAProxy 180이 영향을 받는다.
- DB 서버들이 같은 물리 장비의 자원을 공유하므로 동시 쓰기 시 자원 경합을 확인한다.
- 모니터링 서버 장애 시 해당 서비스의 수집·조회에 영향이 발생한다. 물리 호스트 장애 범위는 실제 배치를 기준으로 확인한다.
- 프록시 분산 배치만으로 자동 장애 전환이 제공되지는 않는다.
- DB 복제와 애플리케이션 이중화는 포함하지 않는다.
- 백업 및 장기 보관용 저장소는 별도로 확보해야 한다. VM 스냅샷은 백업을 대체하지 않는다.

### 7. 재검토 조건

다음 상황에서는 이 ADR의 리소스 할당 또는 배치를 재검토한다.

- 실제 하드웨어 사양이 산정 가정과 다른 경우
- DB 데이터가 초기 저장 예산에 근접하는 경우
- 두 DB의 동시 쓰기로 디스크 병목이 발생하는 경우
- Prometheus 시계열 수 또는 Loki 로그 유입량이 증가하는 경우
- FastAPI에서 모델이나 대용량 데이터를 메모리에 적재하는 경우
- 장기 데이터 보관, 서비스 이중화 또는 자동 장애 전환이 필요한 경우
