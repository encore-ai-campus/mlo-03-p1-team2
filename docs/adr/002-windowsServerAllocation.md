# ADR-002: 상시 운영을 위한 Windows PC 3대의 서버 재배치 및 자원 할당

| 항목 | 내용 |
|---|---|
| 상태 | 채택됨 — 현재 VM 할당 기준 |
| 작성일 | 2026-11-09 |
| 이전 결정 | [ADR-001: VMware 서버 배치 및 리소스 할당](serverSpec.md) |
| 변경 대상 | 운영 장비, 물리 PC별 서비스 배치, VM별 CPU·메모리·디스크 할당 |
| 적용 범위 | 학습·개발 및 소규모 서비스 환경 |

## 1. 변경 배경

초기 구성에는 Mac PC 1대가 포함되어 있었다. 그러나 해당 장비는 개인이 휴대하는 컴퓨터여서 운영 장소에 계속 두거나 항상 켜둘 수 없었다. 서버가 개인 장비의 이동과 전원 상태에 영향을 받는 구성을 바꿀 필요가 있었다.

운영 호스트를 동일 사양의 Windows PC 3대로 변경하고, DB·웹·애플리케이션 서버를 다시 배치했다. Mac은 운영 호스트에서 제외한다.

기존 `serverSpec.md`는 초기 검토 기록으로 보존한다. 이 문서는 그 이후 변경된 서버 구성과 할당 근거를 기록한다.

## 2. 변경 전후

| 구분 | 이전 결정: ADR-001 | 현재 구성 |
|---|---|---|
| 운영 장비 | 일반 PC 2대와 Mac 1대를 전제로 산정 | 동일 사양의 Windows PC 3대 |
| PC 1 | Nginx 2대, NginX 프록시 1대 | Nginx 3대, Loki 1대  |
| PC 2 | MariaDB 2대, MongoDB 1대 | MariaDB 3대, MongoDB 1대, HAProxy 1대 |
| PC 3 | FastAPI 2대, NginX 1대 | Python/FastAPI 서버 2대, Nginx 1대, Grafana 1대, Prometheuse 1대 |
| PC 4 | 모니터링 VM, Prometeuse 1대, Loki 1대, Grafana 1대 |
| 웹·애플리케이션 | Nginx와 FastAPI를 같은 VM에 배치 | 각각 별도 VM과 별도 물리 PC에 배치 |
| 로그 저장 | Grafana·Prometheus·Loki 통합 VM에 RAM 10GB | Loki VM에 RAM 10GB를 별도 할당 |

현재 배치는 위 표를 기준으로 한다. VM은 총 14대이며, 세부 할당값이 확인되지 않은 항목은 아래에 구분했다.

## 3. 운영 장비와 VM 할당

PC 3대는 모두 Windows 호스트이며, Intel Core i5-1340P, RAM 32GB, 디스크 500GB로 사양이 같다. VMware에서 서비스별 VM을 나누어 운영한다.

다음 CPU·메모리·디스크 값은 **VM 한 대 기준**이며, 게스트 OS 사용분을 포함한다.

| 물리 장비 | 서비스 | VM 수 | vCPU | RAM | 가상 디스크 |
|---|---|---|---:|---:|---:|
| PC 1 | Nginx | 2대 | 4 | 6GB | 25GB |
| PC 1 | Nginx | 1대 | 미확인 | 미확인 | 미확인 |
| PC 1 | Loki | 1대 | 4 | 10GB | 미확인 |
| PC 2 | MariaDB | 3대 | 2 | 6GB | 30GB |
| PC 2 | MongoDB | 1대 | 2 | 6GB | 30GB |
| PC 2 | HAProxy | 1대 | 1 | 2GB | 10GB |
| PC 3 | Python / FastAPI | 2대 | 4 | 6GB | 25GB |
| PC 3 | Nginx·Grafana·Prometheus | 각각 1대, 총 3대 | 미확인 | 미확인 | 미확인 |

Nginx는 전체 4대 중 기존에 할당값을 확인한 2대만 수치를 기재했다. 나머지 2대와 Grafana·Prometheus의 자원, Loki의 디스크 용량은 실제 설정을 확인해 보완한다.

## 4. 배치 및 할당 근거

웹, DB, API를 물리 PC별로 나누어 관리와 배포를 단순하게 했다. 각 서비스는 별도 VM으로 실행하므로 설정 변경이나 재시작도 VM 단위로 진행할 수 있다.

**DB는 메모리와 호스트 여유분을 함께 고려했다.** PC 2의 DB 4대에 각각 6GB, HAProxy에 2GB를 할당하면 합계 26GB로, Windows와 VMware에 6GB를 남길 수 있다. DB당 8GB를 주면 합계가 34GB가 되어 물리 메모리를 초과한다. CPU는 DB당 2개를 배정하고, 데이터와 인덱스·로그를 저장할 디스크는 각각 30GB로 시작했다.

**Nginx와 FastAPI는 동시 요청 처리와 실행 환경에 여유를 두었다.** 할당값을 확인한 VM은 각각 4 vCPU와 RAM 6GB를 사용한다. Nginx는 정적 파일 제공과 API 요청 전달을, FastAPI는 요청 검증과 업무 처리를 담당한다. 디스크 25GB에는 OS, 배포 파일 또는 Python 실행 환경, 운영 로그를 저장한다. 이 값은 초기 운영과 부하 검증을 위한 할당이며, 실제 사용량에 따라 조정한다.

**Loki는 로그 저장과 조회 부하를 고려해 RAM을 더 크게 잡았다.** 여러 VM의 로그를 수집하면서 조회도 처리하므로 4 vCPU와 RAM 10GB를 배정했다. HAProxy는 연결 중계와 헬스체크가 주 역할이어서 1 vCPU, RAM 2GB, 디스크 10GB로 구성했다.

## 5. 운영 시 확인할 점

PC 1은 확인된 Nginx 2대와 Loki에 RAM 22GB가 할당되어 있다. 나머지 Nginx 1대의 할당량까지 합쳐 호스트 메모리가 부족하지 않은지 확인해야 한다. PC 3도 FastAPI 2대의 12GB 외에 Nginx·Grafana·Prometheus의 메모리를 추가로 계산해야 한다.

각 PC의 디스크 500GB는 Windows와 VM 이미지가 함께 사용하는 전체 용량이다. VM별 할당 용량뿐 아니라 실제 남은 공간과 스냅샷 크기를 확인하고, DB·로그 데이터가 계속 쌓이지 않도록 보관 기간과 백업을 관리한다. Loki의 디스크 용량은 실제 설정 확인 후 기록한다.

배포 후에는 호스트의 CPU·메모리·디스크 사용량과 API·DB 응답 시간을 함께 확인해 자원을 조정한다.

## 6. 보완점: 같은 서비스의 인스턴스를 여러 물리 PC에 분산

현재는 같은 역할의 서버가 한 물리 PC에 모여 있다. 관리하기에는 편하지만, VM을 여러 대 만들었어도 해당 PC가 꺼지면 그 계층의 서버가 모두 중단된다.

| 장애 장비 | 함께 중단되는 서비스 |
|---|---|
| PC 1 | Nginx 3대와 Loki |
| PC 2 | MariaDB 3대, MongoDB, HAProxy |
| PC 3 | FastAPI 2대, Nginx, Grafana, Prometheus |

웹·API·DB 중 한 계층 전체가 멈추면 요청을 끝까지 처리할 수 없어 예매 서비스가 중단된다. 특히 MariaDB를 3대 운영하더라도 모두 PC 2에 있으면 PC 2의 장애에는 대응할 수 없다.

**다음 단계에서는 웹·API 인스턴스와 DB 복제 노드를 여러 물리 PC에 나누어 배치해야 한다.** 각 계층에 서로 다른 PC에서 실행되는 인스턴스를 두고, 프록시의 장애 전환과 DB 복제·복구 절차도 함께 검증해야 한다. 이렇게 해야 한 PC가 중단되어도 다른 PC의 인스턴스가 요청을 이어받을 수 있다. MongoDB와 프록시 자체의 이중화, 모니터링 서비스의 장애 영향도 함께 검토해 물리 호스트 장애에 대응하는 고가용성 구성을 보완한다.
