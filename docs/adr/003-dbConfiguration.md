# ADR-003: DB 접속 관리와 장애 대응을 위한 MariaDB 구성 변경

| 항목 | 내용 |
|---|---|
| 상태 | 채택됨 — 구성 변경, 복제·접속 전환 검증은 별도 진행 |
| 작성일 | 2026-11-09 |
| 관련 결정 | [ADR-002: Windows PC 서버 배치 및 자원 할당](002-windowsServerAllocation.md) |
| 변경 대상 | MariaDB 인스턴스 수와 DB 접속 경로 |

## 1. 변경 배경

부하 테스트에서는 대부분의 요청이 안정적으로 처리됐다. 최근 [전체 재실행 결과](../loadTestResult_claude_full4.md)에서도 조회·예매·결제와 지속 부하를 포함한 13개 단계가 모두 통과했고, 5xx 오류는 0건이었다. 테스트한 범위에서 DB 처리 용량을 급히 늘려야 할 근거는 크지 않았다.

다만 정상적으로 실행 중인 서버가 부하를 처리하는 것과, 서버를 점검하거나 재시작할 때 서비스를 유지하는 것은 별개의 문제다. 이번 변경은 현재의 안정성을 유지하면서 DB 접속 대상을 관리하고, 노드 중단과 복구에 대응할 수 있는 운영 구조를 마련하는 데 목적을 두었다.

## 2. 변경 내용

| 항목 | 변경 전 | 변경 후 |
|---|---|---|
| MariaDB | 2대 | 3대 |
| DB 접속 진입점 | DB 접속 대상을 애플리케이션에서 관리 | HAProxy를 통한 접속 진입점 단일화 |
| MongoDB | 행동 이벤트 저장용 1대 | 기존 역할과 수량 유지 |

MariaDB 3대와 HAProxy 1대를 배치하고, 애플리케이션이 HAProxy를 통해 DB에 접속하는 구성을 선택한다. 인스턴스별 자원과 물리 PC 배치는 ADR-002를 따른다. 실제 접속 경로 반영 여부는 애플리케이션의 DB 주소와 HAProxy 설정을 대조해 확인한다.

## 3. 변경 이유

### 점검과 재시작을 고려한 구성

DB는 운영 중 설정 변경이나 재시작이 필요할 수 있다. 한 노드를 점검 대상에서 제외하더라도 나머지 두 노드를 접속 대상으로 둘 수 있는 구성을 목표로 MariaDB를 3대로 늘렸다. 이를 바탕으로 노드 중단, 접속 전환, 복귀 후 데이터 동기화 과정을 검증한다. 실제 사용 가능한 노드의 조건은 복제 방식과 각 노드의 데이터 상태에 맞춰 정해야 한다.

### DB 접속 대상 관리 단순화

HAProxy를 DB 앞에 두면 애플리케이션은 일정한 접속 주소를 사용하고, 개별 DB의 추가·제외는 프록시에서 관리할 수 있다. 점검할 서버를 접속 대상에서 빼거나 정상 노드로 새 연결을 보내는 작업도 한곳에서 처리할 수 있다. 헬스체크로 비정상 서버를 연결 대상에서 제외할 수 있지만, DB가 실제로 읽기·쓰기를 처리할 준비가 됐는지도 확인해야 한다. [HAProxy 헬스체크 문서](https://www.haproxy.com/documentation/haproxy-configuration-tutorials/reliability/health-checks/)

### 운영 상황까지 검증 범위 확대

기존 부하 테스트로 확인한 안정성을 기준으로 삼고, 다음에는 노드가 빠지거나 다시 합류하는 상황을 시험한다. 정상 상태의 처리량뿐 아니라 전환에 걸린 시간, 요청 실패 여부, 예매·결제 데이터의 정합성까지 확인하는 것이 이번 구성 변경의 후속 과제다.

## 4. 검증 범위와 주의할 점

MariaDB를 3대 실행하고 HAProxy를 추가하는 것만으로 데이터 복제나 자동 장애 전환이 완성되지는 않는다. 복제 방식과 정상 노드 판정 기준을 확인한 뒤 접속 전환을 검증해야 한다. 기존 연결이나 진행 중인 트랜잭션이 끊기는 상황도 별도로 확인한다.

변경 후에는 같은 부하 조건으로 다시 측정하고, DB 노드 한 대를 중단·복귀시키면서 접속과 데이터가 정상적으로 회복되는지 확인한다. 기존 테스트의 성공 결과를 변경 후 성능 향상이나 장애 대응이 검증된 결과로 사용하지 않는다.

## 5. 결론 및 보완점

부하 테스트에서는 안정적으로 동작했지만, 운영 중 DB를 점검하거나 재시작해야 하는 상황도 고려할 필요가 있었다. 이번 변경은 DB 접속 대상을 한곳에서 관리하고, 노드 중단과 복구에 대비하기 위해 진행했다.

다만 **HAProxy가 1대라는 단일 장애점(SPOF)은 남아 있다.** MariaDB 3대가 모두 정상이어도 HAProxy가 멈추면 애플리케이션이 DB에 접속할 수 없어 예매·결제 서비스가 중단된다. DB를 여러 대 두는 것만으로 접속 경로 전체의 장애에 대응할 수는 없다.

물리 장비도 마찬가지다. 현재 MariaDB와 HAProxy가 모두 PC 2에 있어, PC 2가 꺼지면 DB와 프록시가 함께 중단된다.

다음에는 DB 복제 노드를 여러 물리 PC에 나누고, HAProxy도 다른 PC에 한 대 더 두는 방식으로 보완해야 한다. 프록시를 두 대 배치하는 데서 끝내지 않고, 한쪽이 멈췄을 때 기존 접속 주소를 통해 다른 프록시로 연결되는 구성까지 갖춰야 한다. 이후 DB 노드·HAProxy·물리 PC를 각각 중단해 보면서 접속 전환과 데이터 정합성을 확인한다.
