## 2. 실행 조건과 계획서 대비 변경점

사용자 지시로 계획서 원안 중 다음을 바꿨다.

| 항목 | 계획서 | 이번 실행 |
| --- | --- | --- |
| 페르소나 | 기존 100 + 신규 200 = 300명 | 기존 100 + 신규 100 = **200명** (`personas.json`, `metadata.count` 200) |
| 부하 계정 | 300명 | **신규 100명만** 새로 가입해서 사용. 기존 100명 계정은 사용·변경하지 않음 |
| 동시 접속 단계 | 1 → 10 → 25 → 50 → 100 → 150 → 200 → 300 | 1 → 10 → 25 → 50 → **100** |
| 결과 파일 | `docs/loadTestResult.md` | `docs/loadTestResult_claude.md` |

실행 중 바꾼 사항과 그 이유:

1. **VU 시작 방식 (21:08 변경).** 처음에는 각 단계의 VU를 한 순간에 모두 출발시켰다. 조회 100 VU 단계에서 60초 휴식 직후
   VU 100개가 동시에 TLS 연결과 266KB 목록 요청을 보냈고, 시작 5초 만에 "최근 60초 p95 3초 초과"로 자동 중단됐다
   (목록 p50 2,494ms, 처음 2초 이후 p50 322ms로 회복 중이었다). 60초 판정 구간에 시작 순간의 몰림만 들어 있었고,
   0 → 100 동시 진입은 계획서의 단계 증가(50 → 100)가 아니라 급증에 가깝다. 그래서 이후 모든 단계 증가·지속 부하는
   **30초에 걸쳐 VU를 늘리도록** 바꾸고 조회 100 VU를 다시 측정했다. 중단 기록은 원본 그대로 보존했다(4장 표의 첫 번째 `read-100vu`).
2. **정지 처리.** 위 변경을 위해 `STOP` 파일로 실행을 멈췄다. 이때 혼합 10 VU 단계는 요청 0건으로 끝나서 무효 처리했고, 다시 처음부터 실행했다.

  - 30초마다 DB 실제 건수로 하한을 올리고, 단계 사이에는 DB 건수로 정확히 맞췄다.

## 6. 데이터 정합성

`syntheticData/loadtest/verify_load.py`로 DB를 읽어서 대조했다. 결과는 **통과**다.

- 예매 1,217건 모두 결제 1건과 짝이 맞는다. 상태 조합: `REQUESTED/PENDING` 845건, `CONFIRMED/COMPLETED` 372건. 결제 금액도 예매 금액과 같다.
- 상태 이력: 모든 예매가 허용된 전이만 갖는다. 최종 상태가 예매·결제 상태와 같고, 업무 이벤트 수가 이력과 맞는다.
- `(user_id, request_key)` 중복 0건. 실행기가 201로 받은 예매는 모두 DB에 있고, 실행기가 모르는 예매는 0건이다.
- 행동 로그: 202 응답을 받은 배치의 이벤트 16,124건이 모두 저장됐다(누락 0). `accepted` 합계가 전송 건수와 같고 중복 저장은 0건이다.
  장애 중 실패한 배치의 이벤트 288건은 저장되지 않았다.
- 장애 중 타임아웃된 쓰기(예매 생성 12건, 결제 완료 12건 등)는 저장 여부를 알 수 없었다. 단계 종료 후 DB 건수로 확인했고, 응답 없이 저장된 예매는 없었다.

**검증하지 못한 것:** 계획서의 정합성 전용 시나리오는 실행하지 않았다. 같은 키 동시 예매 8건, 결제·취소 동시 요청, 같은 이벤트 재전송이 이에 해당한다.
일반 부하에서는 같은 키를 재사용하지 않으므로, 위 결과로 중복 방지나 경합 처리를 입증했다고 볼 수 없다.

## 7. 병목과 장애 분석

### 7.1. 조회 부하의 병목: 목록 API와 FastAPI CPU

- 인기순 목록은 680개 공연 전체를 한 번에 돌려준다(응답 약 266KB). 정렬을 위해 `events` 테이블을 매 요청마다 집계한다.
- 50 → 100 VU에서 처리량은 85.6 → 156 RPS로 늘었다. 그동안 FastAPI CPU는 34% → 76%로 올랐고 MariaDB는 20%에 그쳤다.
  병목은 DB가 아니라 FastAPI의 응답 생성(직렬화)으로 보인다.
- 다만 발생기 프로세스 CPU가 조회 100 VU에서 1코어 기준 평균 60%, 순간 최대 97%였다. 측정 지연의 일부는 발생기 쪽에서 생겼을 수 있다.

### 7.3. 실행기 결함 (자동 중단이 동작하지 않음)

  - 타임라인 기록
