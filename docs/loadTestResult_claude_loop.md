## 3. 새로 발견한 문제 — 응답 후 세션을 닫다가 데드락 오류

**현상**
- 19:04:04–05(정합성 단계)에 176에서 `ERROR: Exception in ASGI application`이 2건 났습니다.
- 원인은 `pymysql.err.OperationalError: (1213, 'Deadlock found ...')`이고, 발생 위치는 `get_db()`의 `db.close()` → rollback입니다.
- 두 건 모두 같은 예약에 complete와 cancel이 동시에 들어온 세트였고, 두 요청 모두 이미 `200 OK`를 보낸 뒤였습니다.

**영향**
- 클라이언트는 정상 응답을 받았습니다. 부하기 기록에 500이 없습니다.
- 동시 변경 10건의 최종 상태와 이력도 정합성 검증을 통과했습니다.

**원인 (코드)**
- `_change_once`는 처음에 `SELECT ... FOR UPDATE`로 예약 행을 잠급니다.
- 그런데 아래 세 경우에는 commit이나 rollback 없이 함수를 빠져나갑니다.
  - 이미 원하는 상태여서 그대로 돌려주는 경우(200)
  - 409, 404를 반환하는 경우
- 그래서 트랜잭션과 행 잠금이 응답을 보낸 뒤 의존성 정리 단계(`db.close()`)까지 남아 있습니다.
- 이 사이에 데드락이 나면 오류가 재시도 처리 범위 밖에서 터져 ASGI 오류로 기록됩니다. 잠금을 쥐고 있는 시간도 그만큼 길어집니다.

**제안**
- 일찍 빠져나가는 경로에서도 트랜잭션을 함수 안에서 끝내야 합니다.
  - 이미 원하는 상태여서 그대로 돌려줄 때는 `db.commit()`을 호출합니다. 바뀐 내용이 없으니 잠금만 풀립니다.
  - `HTTPException`이 나는 경우에는 `_with_retry`가 rollback한 뒤 다시 던집니다.
- 이렇게 하면 데드락이 재시도 범위 안에서 처리되고, 응답을 보내기 전에 잠금이 풀립니다.

**수정 (2026-11-08, 미배포)**
- `_with_retry`에서 트랜잭션을 직접 닫도록 바꿨습니다.
  - `work()`가 정상으로 끝났는데 트랜잭션이 아직 열려 있으면 `commit()`합니다. 변경이 없으면 잠금만 풀립니다.
  - `HTTPException`이 나면 `rollback()` 뒤 다시 던집니다.
  - 이 commit은 재시도용 try 블록 안에 있어서, 여기서 1213이 나도 재시도됩니다.
- 예약 생성 쪽의 같은 키 재전송(replay)과 409 경로에도 같은 방식이 적용됩니다.
- 추가한 테스트(`tests/test_reservations.py`) 2개:
  - `test_transaction_is_closed_before_response_on_every_exit`: 아래 여섯 경우 모두 의존성을 정리할 때 트랜잭션이 닫혀 있는지 확인합니다.
    - 같은 키로 다시 보낸 생성 요청(200)
    - 같은 키를 다른 내용으로 보낸 요청(409)
    - 결제 완료(200)와 같은 완료 요청 재전송(200)
    - 취소된 예약에 대한 완료 요청(409)
    - 없는 예약(404)
  - `test_deadlock_when_closing_unchanged_transaction_is_retried`: 변경 없는 경로의 commit에서 1213이 나도 재시도한 뒤 200을 돌려주고, 이력이 중복되지 않는지 확인합니다.
- 수정을 빼고 돌리면 두 테스트 모두 실패하는 것을 확인했습니다. 전체 백엔드 테스트 60개가 통과합니다.

## 5. 결론

- 서버 쪽에서는 데드락 재시도와 랭킹 인덱스가 반영된 상태로 전 구간을 500/502 0건으로 처리했습니다. 정합성 검증도 통과했습니다.
- `read-100vu` 불합격은 부하 발생기 문제로, 서버 성능이 나빠진 것이 아닙니다.
  - 같은 서버를 대상으로 오늘 오전 같은 단계에서 166 RPS, list p95 104ms가 나왔습니다.
- 3절의 세션 정리 오류는 지금은 영향이 없지만, 고치는 것을 권합니다. 잠금을 오래 쥐는 문제와, 오류가 재시도 범위 밖에서 나는 문제가 함께 풀립니다.
