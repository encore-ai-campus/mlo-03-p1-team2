## 4. 판단 (당시 추정, 4.2절에서 정정)

> 이 절의 "배포된 서버가 수정본이 아님", "데드락이 아님"이라는 판단은 틀렸다. 서버 로그로 확인한 원인은 4.2절에 있다.

- 수정본 코드라면 같은 키 경합의 `IntegrityError`는 잡혀서 200이 된다.
  - 로컬 테스트 2개가 통과했다(그중 하나는 실제 동시 요청).
  - 수정 전 코드는 실제 MariaDB에서 8건 중 7건이 `IntegrityError 1062`로 실패하는 것을 재현했다.
- 수정 후에도 500이 남을 다른 경로는 찾지 못했다.
  - 데드락: `Innodb_deadlocks` 0 (전후 0)
  - 잠금 대기 시간 초과: 응답이 수십 ms였다
  - 롤백 뒤 재조회 실패: REPEATABLE READ에서도 롤백 뒤 새 트랜잭션이라 먼저 저장된 행이 보인다
- 500 비율은 37.5%(30/80)에서 20%(16/80)로 줄었다. 두 대 중 **한 대만 수정본으로 바뀌었거나**, 일부 worker가 재시작되지 않은 경우와 맞는다. 다만 응답에 서버 구분 헤더가 없어 어느 서버가 500을 냈는지는 알 수 없다.

확인 요청:

1. 175와 176 각각에서 `app/api/routes/reservations.py`의 `create_reservation`을 확인한다. `db.flush()`가 `try:` 안에 있어야 한다.
2. 두 서버 모두 uvicorn/gunicorn 프로세스를 재시작했는지 확인한다(프로세스 시작 시각).
3. 13:06:05~13:07:07, 13:39:30 전후 FastAPI 오류 로그에서 예외 종류를 확인한다. 같은 키 경합은 `IntegrityError 1062`, 결제·취소 경합은 원인 미확인이다.

수정이 두 서버에 다 적용된 것이 확인되면 정합성 시험만 따로 다시 돌릴 수 있다(`run_load.py run --phases consistency`, 약 1분).

**결론**

- **결제·취소 경로는 수정하지 않았는데, 로컬에서는 500이 없고 운영 서버에서만 25~33% 나온다.**
- 따라서 운영 FastAPI 서버가 저장소와 다른 것으로 보인다. 다를 수 있는 것은 실행 중인 코드, 라이브러리 버전, DB 드라이버·연결 설정, worker 구성이다.
- 운영에서 확인할 것:
  1. 175·176 각각의 커밋과 수정 상태 (`git rev-parse HEAD`, `git status`, `git diff`)
  2. `pip freeze`의 SQLAlchemy·PyMySQL·FastAPI·Starlette 버전
  3. `DATABASE_URL`의 드라이버 부분 (예: `mysql+pymysql`, 비밀번호 제외)
  4. 실행 방식 (uvicorn/gunicorn worker 수)과 15:53:30~15:53:35 오류 로그의 traceback

로컬 재현을 하면서 부하 테스트 계정 하나(`174e08a3…`)로 운영 DB에 예매 8건이 생겼다(같은 키 3건, 경합 5건).

### 4.2. 서버 확인 결과: 원인은 MariaDB 데드락(1213)

175·176에 `test` 계정으로 접속해 읽기 전용으로 확인했다.

**배포 상태**

| 항목 | 175 | 176 | 로컬 |
| --- | --- | --- | --- |
| `app/api/routes/reservations.py` MD5 | `745f47d1…` | `745f47d1…` | `745f47d1…` (같음) |
| 서비스 재시작 (KST) | 15:51:03 | 15:51:58 | |
| 실행 | uvicorn `--workers 2` | uvicorn `--workers 2` | 프로세스 1개 |
| Python | 3.12 | **3.14** | 3.14 |
| SQLAlchemy / FastAPI / Starlette | 2.1.8 / 0.162.0 / 1.10.0 | 같음 | 같음 |
| PyMySQL | **1.2.3** | **1.2.3** | 2.2.8 |
| 드라이버 | `mysql+pymysql` | `mysql+pymysql` | `mysql+pymysql` |

**정합성 시험 시각(15:53:32~34)의 `journalctl -u tikit-api` 로그**

- 500은 모두 `sqlalchemy.exc.OperationalError: (pymysql.err.OperationalError) (1213, 'Deadlock found when trying to get lock; try restarting transaction')`였다.
  - 175에서 19건, 176에서 12건.
  - `IntegrityError`는 없었다. 즉 첫 번째 수정(flush를 try 안으로 옮김)은 의도대로 동작했다.
- 데드락이 난 위치:
  - `create_reservation`: 86행 `flush()`(INSERT `reservations`·`payments`), 90행 `commit()`(INSERT `status_history`·`events`)
  - `change_reservation`: 130행 `SELECT … FOR UPDATE`, 155행 `commit()`(UPDATE `reservations`, INSERT `status_history`·`events`)
- 12:00 KST 이후 1213 로그는 175에서 94줄, 176에서 56줄이었다(오후 전체 계획 실행 포함).
- 1213은 `IntegrityError`가 아니라 `OperationalError`라서 `except IntegrityError`에 잡히지 않는다. 그래서 그대로 500이 됐다.
- `Innodb_deadlocks` 상태 카운터는 내내 0이었다. 이 서버에서는 이 값으로 데드락을 판단할 수 없다.
- 로컬 재현에서 데드락이 나지 않은 이유는 확인하지 못했다. 로컬은 프로세스 1개였고, 운영은 서버 2대 × worker 2개다.
- 정확한 잠금 순환은 보지 못했다. `SHOW ENGINE INNODB STATUS`는 PROCESS 권한이 필요하고, `innodb_print_all_deadlocks`는 OFF다.

**조치 방향**

1. **데드락 재시도.** MariaDB가 메시지에서 권하는 방식이다("try restarting transaction").
   - 1213(과 잠금 대기 시간 초과 1205)이 나면 롤백하고 트랜잭션 전체를 2~3회 다시 실행한다.
   - 예매 생성은 재시도 전에 같은 키를 다시 조회하므로, 먼저 저장된 예매가 있으면 200이 된다.
   - **반영함(미배포):** `reservations.py`에 `_with_retry`를 추가했다. 예매 생성·결제·취소의 트랜잭션 전체를 최대 3회 실행한다.
     - 재시도 사이에 10~50ms × 시도 횟수만큼 무작위로 기다린다.
     - 테스트 3개를 추가했다(데드락 주입 후 생성 성공, 결제 성공, 3회 초과·다른 오류는 재시도 안 함).
2. 원인 확인용(DB 관리자):
   - `SET GLOBAL innodb_print_all_deadlocks = ON`으로 데드락 그래프를 MariaDB 오류 로그에 남긴다.
   - 또는 진단 계정에 PROCESS 권한을 준다.

### 4.3. 재시도 처리 배포 후 정합성 시험 (19:59, `loadtest-20261107-claude-cons4`)

배포 확인: 175·176의 `reservations.py` MD5가 로컬과 같다(`18b5b7db…`). 서비스는 19:58에 재시작됐다.

| 시험 | 수정 전 | IntegrityError 수정 후 | **재시도 추가 후** |
| --- | ---: | ---: | ---: |
| 같은 키 동시 예매 (80건) | 500 30건 | 500 16건 | **500 0건** (201 10 · 200 70) |
| 결제·취소 경합 (60건) | 500 15건 | 500 15~20건 | **500 0건** (200 41 · 409 19) |

- 데이터 검증을 통과했다.
  - 키마다 예매가 1건만 생겼다.
  - 경합한 예매 10건은 모두 최종 상태가 `CANCELLED/CANCELLED`다.
  - 행동 로그 재전송은 중복 저장되지 않았다.
- 서버 로그에서 데드락(1213)으로 인한 재시도는 175에서 19회, 176에서 15회였다.
  - 모두 첫 번째 재시도(`attempt 1/3`)에서 성공했다.
  - 500 응답과 traceback은 없었다.
- 최대 응답 시간: 같은 키 예매 120ms, 결제 87ms, 취소 85ms. 재시도 대기가 들어갔지만 쓰기 기준 1초보다 훨씬 짧다.
- **동시 요청의 500 문제는 해결됐다.** 데드락 자체는 여전히 생긴다(이번 시험 140건 중 34회).
  - 원인(잠금 순서)은 아직 모른다. `innodb_print_all_deadlocks` 설정으로 확인할 수 있다.
  - 동시 요청이 더 많아지면 3회 안에 끝나지 않을 수 있다.
