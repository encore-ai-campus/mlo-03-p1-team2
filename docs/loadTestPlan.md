# 부하 테스트 계획 및 실행 요청 방법

작성일: 2026-11-06

상태: 실행 조건 확정, 실행 도구 준비 및 부하 테스트 미실행. 이 문서는 팀원이 이전 대화 없이 실행을 요청할 수 있는 공통 기준이다. 콘서트·야구 집중 시나리오를 포함한다. 결과 파일은 `docs/loadTestResult.md`로 작성한다.

## 1. 목적과 검증 범위

공연 조회, 예매, 모의 결제, 행동 로그 적재에 부하를 주어 처리량과 병목을 확인한다. 급격한 접속 증가 이후 회복과 데이터 정합성도 검증한다.

- 정상 흐름: 조회 → 예매 생성 → 일부 모의 결제 → 내역 조회
- 집중 흐름: 콘서트 `city`, 야구 `baseball` 각각의 공연에 접속 집중
- 정합성: 예매 중복 생성, 결제·취소 경합, 행동 로그 누락·중복
- 현재 개별 좌석 재고·홀드 모델이 없어 좌석 선점·초과 판매 방지는 검증할 수 없다.
- 실제 화면에서 사용하는 `/reservations` 흐름을 기준으로 한다. 결제는 모의 결제다.

## 2. 확정된 실행 설정

아래 설정을 그대로 사용한다. 문서에 기록된 다른 서버 IP로 대상을 바꾸지 않는다. 이 문서에 따른 실행 요청은 아래 범위의 준비·신규 테스트 계정 생성·합성 데이터 생성·부하 전송을 포함한다. 요청자가 푸시 또는 준비 완료까지만 지시했다면 실제 실행은 시작하지 않는다.

| 항목 | 확정값 또는 실행 시 확인 사항 |
| --- | --- |
| 대상 URL·포트 | `https://www.yaaho.kro.kr` (HTTPS 기본 포트 443). 사용자가 지정한 실행 대상 |
| 환경 | 실제 서비스. 기존 회원·거래·페르소나 분석 데이터를 보존 |
| 서버 구성 | 실제 worker 수, CPU·RAM, DB 연결 설정 기록 |
| 최대 동시 가상 사용자 | 최대 300 VU. 1 → 10 → 25 → 50 → 100 → 150 → 200 → 300으로 증가하고 통과한 단계까지만 사용 |
| 데이터 목표 | 이번 실행에서 새로 생성한 전체 DB 레코드 최소 50,000건 |
| 전체 쓰기 상한 | 이번 실행의 신규 DB 레코드 합계 최대 100,000건. 계정 준비·사전 확인·모든 시나리오·지속 부하를 합산 |
| 행동 로그 상한 | 전체 상한 안에서 MongoDB 행동 로그 최대 50,000건. 별도 50,000건을 추가 허용하는 뜻이 아님 |
| 테스트 계정 | 총 페르소나 300명. `syntheticData/personas.json`의 기존 100명을 보존하고 신규 200명만 추가. 서비스 계정 존재 여부를 대조하고 없는 계정만 가입 |
| 지속 부하 시간 | 통과한 최대 부하에서 30분. 중단 기준 또는 쓰기 상한이 먼저 적용됨 |
| 관측 수단 | Grafana `http://192.168.0.188:3000/`. 실제 접근·인증·대시보드 및 서버·DB 지표 수집 여부는 확인 필요 |

### 2.1. 전체 레코드의 계산 기준

`전체 신규 레코드 = 이번 실행에서 새로 저장된 MariaDB 업무 레코드 합계 + MongoDB 행동 로그 문서 수`

- MariaDB는 신규 회원(`users`), 찜(`favorites`), 예매(`reservations`), 결제(`payments`), 상태 이력(`status_history`), 업무 이벤트(`events`)를 각각 실제 생성 행 수로 합산한다. 추가로 생성하는 업무 테이블이 있으면 명세에 포함한다.
- MongoDB는 이번 실행의 고유 `event_id`로 저장된 행동 로그 문서를 센다. 기존 로그, 중복 재전송, 저장되지 않은 실패 요청, 조회 요청, 기존 행의 상태 갱신은 신규 레코드로 중복 계산하지 않는다. 응답 실패에도 실제 저장된 레코드는 반드시 포함한다.
- **예매도 전체 합계에 포함된다.** 예매 한 번에 예매 1행·결제 1행·초기 상태 이력 2행 및 조건에 따른 업무 이벤트가 생성될 수 있다. 모의 결제 완료도 상태 이력·업무 이벤트를 추가할 수 있다. 따라서 예매 횟수와 전체 레코드 수는 다르다.
- MongoDB의 예매 행동 로그와 MariaDB의 예매 레코드는 서로 다른 저장 레코드이므로 각각 한 번씩 센다. Loki·웹서버 접근 로그, 로컬 결과 파일, 기존 100명 회원은 이번 실행의 신규 데이터 건수에 포함하지 않는다.
- 예: 행동 로그 40,000건 + MariaDB 신규 업무 행 20,000건 = 전체 60,000건. 전체 목표를 만족하고 두 상한도 넘지 않는다.
- 전체 50,000건은 최소 목표이고 100,000건은 중단 상한이다. 기존 DB에 이미 저장된 레코드를 더해 목표를 달성했다고 보고하지 않는다.

상한은 단일 실행의 모든 단계와 재개 구간에 공유한다. 각 쓰기 전에 최대로 추가될 행 수와 진행 중 요청의 예약 예산을 확보하고, 타임아웃으로 저장 여부가 불명확한 요청은 DB 대조 전까지 예산을 반환하지 않는다. 여러 VU가 각각 상한을 갖는 방식은 금지한다. 재개 시 저장 결과와 예산을 먼저 대조한다. 상한을 넘어야만 완료할 수 있는 새 거래는 시작하지 않는다.

최소 목표보다 오류·정합성·상한 중단 기준이 우선한다. 목표 미달이면 그대로 보고하고, 예매만 임의로 늘리거나 부하·상한·실행 시간을 무제한 확대하지 않는다. 행동 로그 상한 도달 후에는 로그가 포함된 혼합 흐름을 조용히 바꾸지 말고 중단 사유와 이후 진행 가능 범위를 기록한다.

로컬 개발 서버를 실행해 실제 서비스 대상 대신 측정하지 않는다.

## 3. 도구와 환경

- 로컬 Postman CLI를 우선 사용한다. 현재 확인한 버전은 1.73.0이며, 실행 시 버전과 `postman performance run -h`를 다시 확인한다.
- 성능 실행은 `postman performance run`, 사전 기능 확인은 `postman collection run`을 사용한다. API별 상태·응답 내용 검사도 포함한다.
- 부하 발생기는 가능하면 서비스·DB와 다른 장비에 둔다. 발생기의 CPU·네트워크도 기록한다.
- 실제 접속 경로인 프록시 → Nginx → FastAPI → DB를 우선 측정한다. 실제 배치가 문서와 같은지는 확인이 필요하다.
- 병목 진단이 필요하면 FastAPI 직접 호출과 비교하되, 호출 경로가 다른 결과를 같은 조건으로 해석하지 않는다.
- Playwright는 소수 사용자의 화면 동작 확인에 활용하고, 본 부하는 API 호출로 발생시킨다.
- 로그인은 부하 실행 전에 하고 토큰을 재사용한다. 기본 토큰 만료 설정이 60분이므로 전체 일정에 맞춰 단계별 재인증을 준비한다. 로그인 성능은 별도 측정한다.
- 테스트 계정·데이터는 실행 ID로 추적한다. 토큰·비밀번호·접근 키는 공유 문서나 커밋에 넣지 않는다.
- 기존 페르소나 데이터와 실행 기록은 보존한다. 종료 후 테스트 데이터 삭제도 임의로 수행하지 않는다.

### 3.1. 팀원 공통 준비·재개 절차

1. 저장소의 `AGENTS.md`와 이 문서를 읽는다. 경로는 저장소 기준 상대 경로를 사용한다. 개인 PC의 절대 경로·실행 파일 경로·자격 증명을 공유 파일에 기록하지 않는다.
2. 실행 시점의 코드와 Postman CLI, Python 등 필요한 런타임을 확인한다. `postman`이 PATH에 없으면 현재 사용자 로컬 bin을 확인한다. 도구가 이미 준비됐다고 가정하지 않는다.
3. 실제 서비스와 Grafana 연결, 인증, 서버·DB 지표 수집, 쓰기 결과 대조 접근을 확인한다. DB 주소가 서비스 배포 환경에 대응하는지 확인하며 개인 로컬 DB 설정을 운영 DB 설정으로 간주하지 않는다. 필요한 자격 증명은 실행자의 로컬 환경에서만 제공한다.
4. 실행별 고유 ID를 만들고 대상·전체/행동 예산·계정 매핑·원본 페르소나 스냅샷·입력 해시·시작 기준을 기록한다. 기존 실행 ID나 결과가 있으면 새 실행인지 재개인지 확인하고 임의로 덮어쓰거나 재실행하지 않는다. 기존 보고서는 같은 경로에 새 결과를 작성하기 전에 실행별 보관 디렉터리에 보존한다.
5. `personas.json`이 100명이면 기존 프로필을 유지한 채 신규 200명을 중복 없이 추가하고 `metadata.count`를 300으로 맞춘다. 이미 300명이면 추가하지 않는다. 다른 수라면 기존 데이터를 삭제하지 말고 차이를 보고한다. 생성기를 `--count 300`으로 다시 돌려 원본을 덮어쓰지 않는다.
6. 현재 `run.py`는 최대 100명, `run_periods.py`는 기존 100명으로 제한되고 입력 해시를 검증한다. JSON 변경만으로 300명 실행이 가능하다고 가정하지 않는다. 신규 추가·계정 매핑·입력 버전 보존과 부하 전용 실행 도구를 준비·검증한다. 기존 실행의 재개·검증 기능을 깨뜨리지 않는다.
7. 실제 서비스에서 기존 합성 계정의 존재와 신원을 대조한다. 다른 팀원이 계정·비밀번호 파일을 갖고 있지 않으면 로컬로 제공받는다. 같은 이메일로 무작정 재가입하거나 기존 비밀번호를 재설정하지 않는다. 신규로 필요한 계정만 생성하고 이번 실행에서 만든 회원 수를 전체 예산에 포함한다.
8. 컬렉션, VU별 데이터 분리, 공유 쓰기 예산, 구간별 중단 감시와 종료 수단을 준비하고 작은 실행으로 검증한다. Postman 컬렉션 변수를 VU 간 전역 카운터로 간주하지 않는다. 성능 도구의 지원 범위가 부족하면 이를 설명하고 조건을 만족하는 실행 방법을 마련한다.
9. 사전 확인부터 단계적으로 실행하고 결과를 `docs/loadTestResult.md`에 작성한다. 계정·접근 정보 또는 필수 계측이 없어 실행할 수 없는 부분은 구체적으로 기록하고, 준비된 항목까지 보존한다. 관측·상한 제어가 준비되지 않은 상태에서 실제 서비스에 고부하를 보내지 않는다.

한 서비스에 여러 팀원이 동시에 독립 실행하지 않는다. 실행 담당자 한 명이 순서대로 진행한다. 여러 발생기를 함께 쓰려면 단일 공유 예산과 실행 조정 기능이 필요하며 이 문서의 기본 범위에 포함하지 않는다. 문서의 프롬프트는 에이전트에게 준비와 실행을 요청하는 방법이며, 아직 만들어지지 않은 실행기나 인증 정보를 대신하지 않는다.

## 4. 테스트 시나리오

API 경로의 공통 접두사는 `/api/v1`이다.

| 시나리오 | 요청 흐름 | 확인할 내용 |
| --- | --- | --- |
| 조회 | `GET /performances`, 검색·정렬, `/performances/ranking`, `/performances/{id}` | 인기순·랭킹 집계 쿼리와 목록 응답 비용 |
| 예매·결제 혼합 | 상세 → `POST /reservations` → 일부 `POST /reservations/{id}/complete` → 예매·결제 내역 조회 | DB 쓰기, 트랜잭션, 연결 대기 |
| 콘서트 오픈 집중 | `city` 상세·예매·모의 결제 집중 | 단일 공연 요청 급증 시 지연·오류·회복 |
| 야구 오픈 집중 | `baseball` 상세·예매·모의 결제 집중 | 단일 경기 요청 급증 시 지연·오류·회복 |
| 중복 예매 | 같은 회원·같은 `request_key`·같은 내용으로 동시 예매 요청 | 예매·결제·초기 이력 중복 생성 방지 |
| 결제·취소 경합 | 같은 예매에 `complete`·`cancel` 동시 요청 | 허용된 상태 전이와 최종 예매·결제 상태 일치 |
| 행동 로그 | `POST /tracking/events` 배치 전송 및 동일 이벤트 재전송 | MongoDB 적재 성능, 누락·중복 방지 |

공연 ID와 유효한 관람일·회차는 실행 전에 API에서 확인한다. 고정 날짜나 없는 ID로 발생한 404·422를 서버 용량 문제로 해석하지 않는다.

혼합 부하는 **사용자 방문 기준** 조회만 80%, 예매까지 15%, 예매 후 결제까지 5%로 시작한다. 각 흐름에 대응하는 행동 로그도 전송한다. 이는 HTTP 요청 비율과 다르다. 기본 혼합 부하에서는 공연을 분산 선택하고, 집중 시나리오에서만 지정 공연에 몰리도록 한다.

예매마다 새 UUID 요청 키를 사용하고, 중복 검증 시나리오에서만 같은 키를 재사용한다. 계정·예매 ID·토큰을 다른 VU의 값으로 덮어쓰지 않도록 분리한다.

행동 로그 배치는 현재 서버 제한인 최대 10개를 따른다. 합성 표시와 실행 ID를 포함하고 실제 발생 시각을 기록한다. 기존 페르소나 분석용 가상 기간을 성능 측정 시간으로 사용하지 않는다. API로 생성한 로그는 실제 UI에서 발생한 로그와 구분한다.

## 5. 실행 순서

먼저 조회 부하를 측정한 다음 예매·결제 혼합 부하를 측정한다. 각 실행은 독립적으로 결과를 남기며, 기준을 통과한 경우에만 다음 부하로 올린다.

| 단계 | 동시 가상 사용자(VU) | 시간 | 목적 |
| --- | --- | --- | --- |
| 사전 확인 | 1 | 2분 | 연결·인증·유효한 데이터·응답 검사·결과 저장 확인 |
| 기준 측정 | 10 | 5분 | 정상 응답시간과 자원 사용량 확보 |
| 단계 증가 | 25 → 50 → 100 → 150 → 200 → 300 | 각각 5분 | 처리량 증가와 지연 시작점 확인 |
| 콘서트 집중 | 5 → 통과한 최대 VU → 5 | 5분 | 급증과 회복 확인 |
| 야구 집중 | 5 → 통과한 최대 VU → 5 | 5분 | 급증과 회복 확인 |
| 정합성 검사 | 소규모 동시 요청부터 | 건수 제한 | 중복 요청과 결제·취소 경합 결과 확인 |
| 지속 부하 | 앞 단계에서 통과한 최대 VU | 30분 | 메모리·연결·저장량 누적 확인 |

집중 부하는 앞선 단계에서 검증된 최대 VU까지만 Postman `spike` 프로필로 구성한다. 300명이 목표여도 100명까지만 통과했다면 300명 급증을 시도하지 않는다. 현재 CLI 기준 예시는 준비 90초 → 증가 20초 → 감소 40초 → 남은 시간 기본 부하 유지다. 이 프로필은 최고 부하를 지속하지 않는다. 최고 부하 유지가 필요하면 `peak` 프로필을 별도 적용한다.

각 실행 사이에 자원·지연이 기준 수준으로 회복했는지 확인한다. 오류나 포화가 발생하면 다음 단계로 올리지 않고 원인을 분석한다. 고부하 전에 쓰기 예산과 남은 저장 공간을 확인한다.

**300개 페르소나, 300 VU, 300 RPS는 서로 다르다.** 총 300명의 페르소나를 준비하되 동시 접속은 1명부터 올린다. 실제 RPS와 성공 거래 수를 함께 기록하고, 요청 간 대기와 부하 모델도 결과에 명시한다.

## 6. 합격 기준과 중단 기준

아래 값을 기본 판정 기준으로 사용하고, 실제 결과는 API별로 판정한다. 기준을 바꾼 경우 실행 설정과 보고서에 변경 이유를 명시한다.

| 항목 | 초기 합격 기준 |
| --- | --- |
| 조회 응답시간 | p95 500ms 이하 |
| 예매·모의 결제 응답시간 | p95 1초 이하 |
| 정상 요청 실패율 | 타임아웃·서버 오류·응답 검증 실패 합계 1% 미만 |
| 데이터 정합성 | 중복 예매, 예매·결제 상태 불일치, 정상 수락된 로그 누락 0건 |

p99는 반드시 기록한다. 로그 API와 내역 조회도 API별 지연을 기록하고, 필요하면 별도 목표를 정한다. 전체 평균만으로 느린 쓰기 API를 가리지 않는다.

예상된 충돌 응답은 일반 실패와 구분하되, 상태 코드뿐 아니라 응답 내용과 최종 DB 상태를 검사한다. 로그 재전송은 기존 이벤트를 새 문서로 중복 저장하지 않아야 하며 `accepted`·`duplicates` 합계를 요청 건수와 대조한다.

다음 조건에서는 실행 중 부하를 중단한다.

- 정상 요청 실패율이 최근 30초 구간에서 5%를 초과한다.
- p95가 최근 1분 구간에서 3초를 초과한다.
- 데이터 정합성 오류, 서버 재시작, DB 연결 고갈이 확인된다.
- 이번 실행 전체 신규 레코드 100,000건 또는 행동 로그 50,000건 상한에 도달하거나, 다음 쓰기를 위한 예산이 부족하거나 저장 공간이 부족하다.

Postman `--pass-if`는 실행 후 판정용이며 트래픽을 자동 조기 중단하지 않는다. 위 구간별 지표, 쓰기 예산, 서비스 상태를 감시하고 실행을 종료할 수단을 본 부하 전에 준비한다. 준비되지 않았다면 고부하 단계로 진행하지 않는다.

## 7. 관측과 결과물

- 실행 시작·종료 시각(KST), 전체 경과 시간과 단계별 시작·종료 시각
- 1분 단위 목표 VU·실제 활성 VU(수집되는 경우 최솟값/평균/최댓값), 완료 방문 수, 요청 수·RPS·p95·실패율의 시간대별 표
- 집중 부하의 상승·하강은 1분보다 짧으므로, 수집 가능한 더 짧은 간격의 원시 기록과 실제 최대 VU 도달 시각도 보존
- API별 요청 수·성공/실패 수·실제 RPS·p95·p99, 성공 예매·결제 건수
- FastAPI 및 호스트 CPU·메모리, 프록시·Nginx 오류
- MariaDB 연결·잠금 대기·느린 쿼리, MongoDB 쓰기 지연
- 디스크 사용량·I/O 지연과 부하 발생기 CPU·네트워크
- 생성한 예매 ID·결제 상태·금액·이력과 DB 실제 저장 결과 대조
- 고유 이벤트 ID 기준의 MongoDB 적재 건수, 누락·중복 확인

지표를 수집하지 못한 항목은 결과에서 미측정으로 표시한다. HTTP 성공만으로 DB 정합성이나 전체 서버 수용량을 입증했다고 보고하지 않는다.

목표 VU는 설정값이고 실제 활성 VU는 발생기 관측값이다. 둘을 구분하며, 실제 활성 VU가 수집되지 않으면 목표값으로 대체하지 않고 미측정으로 표시한다. VU는 가상 사용자 수이며 동시에 처리 중인 HTTP 요청 수나 누적 방문 수와 다르다. 같은 계정의 반복 방문을 서로 다른 실제 사용자 접속으로 보고하지 않는다.

원시 결과, 실행 설정, 데이터 대조 결과, 요약 보고서를 실행 ID별로 보관한다. 현재 Git에서 제외된 `syntheticData/playwright/artifacts/<실행 ID>/`를 활용할 수 있으나, 기존 실행 디렉터리를 덮어쓰지 않는다. 자격 증명은 결과 공유 전에 제거한다.

최종 보고서는 `docs/loadTestResult.md`에 작성한다. 실행 ID, 대상, KST 시각, 분 단위 접속 인원 표, 통과한 최대 부하, API별 지표, MariaDB 테이블별·MongoDB 컬렉션별 신규 건수와 합계, 최소 목표·두 상한 충족 여부, 병목이 나타난 조건, 중단 이유, 미측정 항목을 포함한다. 관측이 없는 실제 접속 인원이나 DB 건수를 추정값으로 채우지 않는다. 개선 후에는 같은 데이터 규모·호출 경로·설정·요청 구성으로 재측정하되, 데이터 누적의 영향도 기록한다.

## 8. 나중에 입력할 실행 프롬프트

팀원은 저장소를 최신 상태로 받은 뒤 아래 프롬프트를 그대로 입력한다. 앞선 대화 내용을 참조하거나 URL·인원을 다시 채울 필요가 없다. 실행자의 로컬 자격 증명과 사내망 접근은 별도로 필요하며, 부족한 정보만 질문한다.

```text
AGENTS.md와 docs/loadTestPlan.md를 읽고 문서에 확정된 조건대로
부하 테스트 도구를 준비·검증한 뒤 사전 확인부터 단계적으로 실행해줘.

대상은 실제 서비스 https://www.yaaho.kro.kr 이고,
Grafana는 http://192.168.0.188:3000/ 이야.
syntheticData/personas.json의 기존 100명을 보존하고 신규 200명만 추가해
총 300명으로 준비해. 이미 추가돼 있으면 다시 만들지 말고,
실제 서비스 계정도 존재 여부를 대조해 없는 계정만 가입시켜.
기존 프로필·계정 매핑·과거 실행 재현성을 보존하고 필요한 실행기를 준비해.

동시 접속은 1→10→25→50→100→150→200→300명으로 올리고,
각 단계가 문서의 기준을 통과했을 때만 다음 단계로 진행해.
콘서트 city·야구 baseball 집중 테스트도 포함하되,
앞서 통과한 최대 동시 접속 인원을 넘지 마.
지속 부하는 통과한 최대 인원에서 30분으로 해.

이번 실행의 전체 신규 DB 레코드 목표는 최소 50,000건,
전체 상한은 100,000건, 그중 MongoDB 행동 로그 상한은 50,000건이야.
예매·결제·이력·업무 이벤트·신규 회원 등도 전체 합계에 포함해.
계정 준비·사전 확인·모든 단계·재개 구간에 하나의 예산을 적용하고,
진행 중 요청과 저장 여부 불명확한 요청까지 포함해 상한을 지켜.
중단 감시와 쓰기 예산 제어가 검증되기 전에는 고부하를 보내지 마.
목표량보다 중단 기준과 상한을 우선하고 부족하면 미달로 보고해.

기존 데이터·실행 기록을 보존하고 임의 삭제·계정 비밀번호 재설정을 하지 마.
자격 증명은 로컬 환경에서만 사용하고 출력하거나 커밋하지 마.
다른 담당자의 실행이 진행 중이면 중복 실행하지 마.
필요한 접근 정보가 없으면 그 항목만 구체적으로 물어봐.

결과는 docs/loadTestResult.md에 작성해.
기존 보고서가 있으면 먼저 실행별로 보관한 뒤 새 결과를 작성해.
KST 실행 시각, 분 단위 목표·실제 활성 VU, 완료 방문 수,
API별 RPS·p95·p99·실패율, DB별 신규 건수와 전체 합계,
데이터 정합성, 목표·상한 충족 여부, 병목·중단 이유를 정리해.
실측하지 못한 지표는 미측정으로 표시해.
```

문서에 모든 실행 조건이 있으므로 아래 짧은 프롬프트도 새 대화에서 사용할 수 있다.

```text
AGENTS.md와 docs/loadTestPlan.md를 읽고, 문서의 확정 조건과
팀원 공통 준비·재개 절차대로 부하 테스트를 준비·검증하고 실행해줘.
300명 페르소나, 단계적으로 최대 300명 동시 접속,
전체 신규 레코드 최소 5만·최대 10만 건, 그중 행동 로그 최대 5만 건,
콘서트·야구 집중 테스트를 포함하고 결과는 docs/loadTestResult.md에 정리해줘.
```

비밀번호나 토큰을 프롬프트에 붙이지 않는다. 실행자가 준비한 로컬 설정 위치를 지정하거나 누락된 접근 정보에만 답한다. 이전 대화의 설정을 알고 있다고 가정하지 않는다.
