# Tikit 페르소나 기반 사용자 샘플 데이터 생성 설계

## 현재 구현 및 생성 결과 (2026-11-06)

사용자 요청에 따라 `../syntheticData/generatePersonas.py`로 기본 100명(시드 42)의 추천 실험용
프로필을 생성하고 `personas.json`에 UTF-8로 저장했다. 생성기 버전은 `1.2`,
스키마 버전은 `1.1`이다.
성 40개와 이름 96개의 조합에서 중복 없이 추출하여 한 데이터셋 안에서는
이름이 겹치지 않으며 숫자 접미사를 붙이지 않는다. 최대 생성 인원은 3,840명이다.
서로 다른 실행 결과 사이의 이름 중복까지 보장하지는 않는다.

사용자별 `viewing_style`과 이를 설명하는 한 줄 `bio`를 추가했다.
`viewing_style.companion`은 `solo`/`friends`/`partner`/`family`,
`attendance_frequency`는 `occasional`/`monthly`/`frequent`,
`discovery_style`은 `familiar`/`mixed`/`adventurous` 중 하나다.
총 36가지 조합을 각 페르소나 안에서 중복 없이 배정한 후, 해당 페르소나의
인원이 36명을 넘으면 조합을 재사용한다. 기본 100명에서는 페르소나별 20명의
특성 조합과 소개가 서로 다르다. 소개에 쓰는 장르는 실제 선호 카테고리와 일치한다.
이 특성은 합성 설정이며, MBTI나 실제 행동에서 유추한 사실이 아니다.
별도 난수 스트림을 사용해 기존 이름, ID, MBTI, 페르소나, 선호도 점수는 유지한다.

MBTI 16종, 페르소나 5종, 카테고리별 선호도 점수 형식은 유지한다.
점수는 가상의 선호도 가정이며 실제 행동 로그에서 추출한 특성이 아니다.
DB 적재, 회원가입, 행동 이벤트 생성은 수행하지 않았다.
스크립트는 여전히 표준 출력만 사용하며, 결과 파일은 별도로 저장한 산출물이다.

## 페르소나를 이벤트 로그에 활용하는 방법

**현재 구현은 사용자 프로필 생성까지다. 다음 내용은 후속 이벤트 생성기의
제안이며, 이벤트 생성·파일 저장·API 전송·DB 적재 기능은 아직 없다.**
실제 수집 형식과 전송 규칙은 [사용자 행동 이벤트 수집 문서](eventTracking.md)를 기준으로 한다.

### 프로필 필드의 활용

| 필드 | 이벤트 생성 시 활용 |
| --- | --- |
| `id` | 합성 로그와 프로필을 연결하는 키. 실제 회원 DB의 ID와 같다고 가정하지 않는다. |
| `persona` | 생성 결과를 취향 집단별로 비교하는 분석 기준 |
| `category_weights` | 카테고리를 가중 추출하는 기준. 합계 100이며 실제 관측 비율이나 결제 확률은 아니다. |
| `preferred_categories` | 점수가 높은 상위 두 카테고리. 이 두 개만 선택하도록 제한하지 않는다. |
| `viewing_style.attendance_frequency` | 관람 빈도 설정. 사이트 방문 횟수와 구매 횟수는 별도 규칙으로 정해야 한다. |
| `viewing_style.discovery_style` | 익숙한 작품 재탐색과 새로운 작품 탐색의 비율을 정할 때 참고한다. |
| `viewing_style.companion` | 동반 관람 시나리오를 정할 때 참고한다. 동반 유형만으로 구매 수량을 확정하지 않는다. |
| `mbti` | 분석 시 집계 기준. MBTI에 따라 취향·구매율을 고정하지 않는다. |
| `bio` | 사람이 읽는 설명. 생성 규칙은 문장 파싱 대신 위 구조화 필드를 사용한다. |

### 생성 순서 제안

1. 생성 기간, 이벤트 생성용 시드, 방문 횟수 분포, 행동 전환 확률을 정하고 실행 설정에 기록한다.
2. 사용자별 가상 브라우저 식별자와 방문 세션을 만든다. 실제 프론트엔드의 `session_id`는
   탭의 `sessionStorage` 기준이며 시간 제한으로 자동 교체되지 않는다. 합성 로그에서 방문마다
   새 ID를 사용한다면 이를 시뮬레이션 규칙으로 명시한다.
3. `category_weights`로 카테고리를 뽑고 해당 카테고리의 공연을 선택한다.
   공연 ID·카테고리·가격·예매 가능 일정은 사용할 공연 데이터와 맞춘다.
4. 조회, 찜, 예매 시작, 결제 또는 이탈을 시간순으로 생성한다. 모든 조회가 결제로 이어지게 하지 않는다.
   취소는 앞서 생성한 예매에 연결하고, 예매·결제·취소 로그의 `reservation_id`는 일관되게 유지한다.
5. 이벤트 형식, 식별자, 시간 순서, 공연 연결을 검증한 뒤 합성 전용 파일에 저장한다.

한 세션의 예시이며 모든 사용자에게 강제하는 흐름은 아니다.

| 상대 시각 | MongoDB 행동 이벤트 `type` | 행동 |
| --- | --- | --- |
| 00:00 | `page_view` | 메인 접속 |
| 00:08 | `category_select` | 전시 선택 |
| 00:20 | `performance_view` | 전시 공연 상세 조회 |
| 00:45 | `favorite_add` | 찜 추가 |
| 01:10 | `booking_start` | 예매 시작 |
| 01:30 | `reservation_request` | 예매 요청 성공 |
| 02:00 | `payment_complete` | 모의 결제 완료 |

조회 후 이탈, 찜 후 이탈, 예매 중 이탈, 결제 후 취소 등도 별도 경로로 둔다.
실제 화면을 통한 검증에서는 성공한 동작에 대해서만 성공 이벤트를 기록한다.
파일 시뮬레이션의 성공 이벤트는 실제 예매나 결제를 생성했다는 뜻이 아니다.

### 사용자 연결과 저장 방식

- **파일로 생성:** 예를 들어 `syntheticEvents.jsonl`의 각 행을
  `{ "synthetic_user_id": "프로필 id", "event": { ...수집 이벤트 형식... } }`로 구성할 수 있다.
  이는 제안하는 파일 형식이며 API 요청 형식이 아니다. 분석 시
  `synthetic_user_id = users[].id`로 프로필과 연결한다.
- 생성 실행 정보에는 `synthetic: true`, 실행 ID, 프로필 생성 버전·시드,
  이벤트 생성 버전·시드, 생성 기간, 전환 확률, 공연 데이터 버전을 기록한다.
  프로필의 스키마 버전 `"1.1"`과 수집 이벤트의 `schema_version: 1`은 별개다.
- **기존 수집 API로 전송:** 한 요청에 `{"events": [...]}` 형태로 1~10건을 보낸다.
  최상위 이벤트에 `synthetic_user_id`, `user_id`, `mbti` 등을 임의로 추가하면 거절된다.
  `user_id`는 검증된 JWT에서만 추출하며 토큰이 없거나 무효하면 `null`이다.
  실제 테스트 회원과 연결하려면 회원 생성·인증 및 프로필 ID ↔ 회원 ID 매핑이 별도로 필요하다.
- 현재 프로필에는 비밀번호와 동의값이 없으므로 회원가입 요청이나 회원 DB 레코드로
  그대로 사용할 수 없다. 수집 API에 로그를 보내도 회원·예매·결제 레코드는 생성되지 않는다.
- 합성 파일이나 테스트용 DB·컬렉션을 사용해 실제 행동 데이터와 구분한다.
  가중치로 만든 로그에서 같은 취향이 나타나는 것은 생성 규칙의 결과다.
  분석 파이프라인 검증에는 쓸 수 있지만 실제 사용자 취향이나 추천 성능의 근거로 삼지 않는다.

## 1. 목적과 작업 범위

Tikit의 기능 테스트와 데이터 분석에 활용할 가상 사용자 약 100명을 자동 생성한다. 각 사용자에 기본정보, MBTI, 페르소나, 선호 공연 카테고리를 부여한다.

현재 승인된 작업은 이 문서의 신규 작성이다. 기존 파일은 수정하지 않는다. 다음 단계에서는 프로젝트 루트에 독립 실행형 `../syntheticData/generatePersonas.py` 하나를 추가하는 방식을 제안한다. 설계와 실행 예시는 제안 사항이며, 아직 구현된 기능이 아니다.

이번 생성기는 사용자 프로필과 선호도 데이터를 만드는 범위로 한정한다. 회원가입 요청, DB 적재, 로그인, 조회·예매·결제 이벤트 생성은 별도 작업이다. 실제 서비스 화면에서 가상 사용자를 사용하려면 후속 연동이 필요하다.

## 2. 확인한 기존 구조

| 확인 파일 | 현재 구조 및 설계에 미치는 영향 |
| --- | --- |
| `../backend/app/models/user.py` | 사용자 필드: `id`, `name`, `email`, `password_hash`, `mbti`, `consent`, `consented_at`, `created_at`. 페르소나와 선호 카테고리 필드는 없다. |
| `../backend/app/schemas/user.py` | 회원가입에는 이름, 이메일, 비밀번호 및 확인값, 유효한 MBTI, 동의값 `true`가 필요하다. |
| `../backend/app/core/config.py` | MBTI 16종과 공연 카테고리 6종이 정의되어 있다. |
| `../backend/app/db/seed.py` | 공연 초기 데이터 생성용이며 사용자 생성 기능은 아니다. 기존 파일을 수정하거나 실행하지 않는다. |
| `../frontend/src/utils/index.js` | 화면의 카테고리에는 `전체`가 추가되지만, 이는 탐색 필터이므로 선호 카테고리에서 제외한다. |

기존 사용자 테이블에 없는 분석용 필드는 생성 결과에만 담는다. 생성 결과 전체를 기존 회원가입 API나 DB에 그대로 전달할 수는 없다. 비밀번호와 해시를 이 데이터에 포함하지 않으므로 회원가입이나 DB 삽입을 위한 완성된 레코드도 아니다.

## 3. 생성 방식 비교와 권장안

| 방식 | 장점 | 고려 사항 |
| --- | --- | --- |
| Python 표준 라이브러리 기반 규칙 생성 | 설치나 외부 통신 없이 실행 가능하며 시드로 결과 재현 가능 | 페르소나와 분포 규칙을 직접 정의해야 함 |
| Faker 기반 생성 | 다양한 이름과 기본정보 생성에 유용 | 추가 의존성이 필요하며 공연 취향 규칙은 별도로 필요 |
| LLM 기반 생성 | 자유로운 페르소나 서술에 유용 | 외부 호출, 비용, 형식 검증, 재현성 관리가 필요 |

**권장안:** Python 표준 라이브러리 기반의 독립 스크립트. 100명 규모와 기존 파일 수정 금지 조건에 맞고, 테스트마다 동일한 입력을 만들기 쉽다. 아래 상세 설계는 이 방식에 대한 제안이다.

## 4. 데이터 구조

기본 출력은 UTF-8 JSON이며, 생성 설정을 담은 `metadata`와 사용자 목록 `users`로 구성한다.

| 위치 / 필드 | 타입 | 생성 규칙 |
| --- | --- | --- |
| `metadata.schema_version` | 문자열 | 초기 버전 `1.0` |
| `metadata.generator_version` | 문자열 | 초기 버전 `1.0`. 생성 규칙 변경을 추적 |
| `metadata.count` | 정수 | 실제 생성 인원. 기본 100 |
| `metadata.seed` | 정수 | 난수 시드. 기본 42 |
| `metadata.synthetic` | 불리언 | 항상 `true` |
| `users[].id` | 문자열 | 시드와 순번을 입력으로 만든 결정적 UUID. 한 결과 내 고유 |
| `users[].name` | 문자열 | 가상 한국어 이름과 순번 조합. 공백 제거 후 1~30자 |
| `users[].email` | 문자열 | `persona0001@example.com` 형식. 한 결과 내 고유 |
| `users[].mbti` | 문자열 | 기존 설정과 같은 MBTI 16종 중 하나 |
| `users[].persona` | 문자열 | 아래 정의된 페르소나 코드 중 하나 |
| `users[].preferred_categories` | 문자열 배열 | 사용자 선호도 점수가 가장 높은 카테고리 2개. 중복 없음 |
| `users[].category_weights` | 객체 | 카테고리 6종 각각에 대한 양의 정수 점수. 합계 100 |

이름과 이메일은 합성값이다. 현재 사용자 모델에 없는 나이, 성별, 직업, 주소 등은 초기 범위에 추가하지 않는다. `consent`와 동의 시각도 자동 생성하지 않는다. 실제 가입과 연결하는 단계에서 테스트용 처리 방식을 별도로 정해야 한다.

구조 예시이며, 실제 생성 결과는 아니다.

```json
{
  "metadata": {
    "schema_version": "1.0",
    "generator_version": "1.0",
    "count": 100,
    "seed": 42,
    "synthetic": true
  },
  "users": [
    {
      "id": "602a118d-19ea-5374-b847-d0830f34aeb1",
      "name": "김하늘0001",
      "email": "persona0001@example.com",
      "mbti": "ENFP",
      "persona": "live_fan",
      "preferred_categories": ["콘서트", "뮤지컬"],
      "category_weights": {
        "콘서트": 40,
        "뮤지컬": 20,
        "스포츠": 15,
        "전시": 10,
        "클래식": 5,
        "연극": 10
      }
    }
  ]
}
```

## 5. 페르소나와 선호 공연 카테고리

페르소나는 공연 취향을 구분하기 위한 테스트용 가정이다. MBTI와 공연 선호 사이의 실제 통계나 인과관계를 의미하지 않는다. MBTI는 페르소나와 독립적으로 배정하여 특정 MBTI의 취향이 고정되지 않게 한다.

| 페르소나 코드 | 설명 | 콘서트 | 뮤지컬 | 스포츠 | 전시 | 클래식 | 연극 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `live_fan` | 라이브 공연 애호가 | 40 | 20 | 15 | 10 | 5 | 10 |
| `story_lover` | 이야기와 무대 연기 선호 | 10 | 35 | 5 | 10 | 10 | 30 |
| `sports_fan` | 스포츠 관람 선호 | 15 | 5 | 55 | 10 | 5 | 10 |
| `art_explorer` | 전시와 예술 탐색 선호 | 10 | 10 | 5 | 45 | 20 | 10 |
| `classic_lover` | 클래식 감상 선호 | 10 | 10 | 5 | 20 | 45 | 10 |

각 행의 합은 100이며 개인별 점수의 기준값으로 사용한다. 같은 페르소나 안에서도 차이가 나도록 각 카테고리 점수에 -3~+3의 정수 변동을 주고, 최소 1점을 보장한다. 이후 합계 100으로 정규화한다. 정수 변환 시 버림 후 소수 부분이 큰 순서대로 잔여 점수를 배분하며, 동점은 기존 카테고리 순서로 처리한다.

`preferred_categories`는 최종 점수 내림차순 상위 2개로 정한다. 동점은 기존 카테고리 순서인 콘서트, 뮤지컬, 스포츠, 전시, 클래식, 연극 순으로 처리한다. 점수는 추후 행동 시뮬레이션에서 선택 확률로 사용할 수 있지만, 이번 범위에서 관람·구매 행동을 생성하지는 않는다.

## 6. 생성 절차와 재현성

1. 인원과 시드를 검증한다. 인원은 양의 정수만 허용한다.
2. `random.Random(seed)`로 지역 난수 생성기를 만든다. 외부 API나 DB에 접근하지 않는다.
3. 페르소나 5종을 균등 배정한다. 기본 100명에서는 각각 20명이다. 나머지가 있으면 시드로 섞은 페르소나 순서에 따라 1명씩 추가 배정한다.
4. MBTI 16종도 균등 배정한다. 기본 100명에서는 유형별 6~7명이며, 추가 1명을 받을 4개 유형은 시드로 결정한다.
5. 페르소나 목록과 MBTI 목록을 각각 독립적으로 섞어 사용자에게 배정한다. 모든 MBTI×페르소나 조합의 출현까지 보장하지는 않는다.
6. 순번으로 이름과 이메일을 만들고, 고정 네임스페이스에서 시드와 순번을 입력으로 UUID를 만든다.
7. 개인별 카테고리 점수와 선호 카테고리를 계산한다.
8. 구조와 분포를 검증한 후 JSON을 표준 출력으로 내보낸다. 오류 설명은 표준 오류로 내보내고 실패 종료 코드를 반환한다.

같은 생성기 버전, Python 버전, 인원, 시드에서는 같은 결과를 만들도록 구현한다. 현재 시각이나 무작위 UUID는 사용하지 않는다. 다른 인원으로 실행할 때 기존 결과의 앞부분이 유지되는 것은 보장하지 않는다. 이메일은 실행별로 재사용되므로 서로 다른 실행 결과를 합칠 경우 중복 처리가 필요하다.

## 7. 실행 및 저장 방법 제안

다음 명령은 `../syntheticData/generatePersonas.py` 구현 승인 및 완료 후 프로젝트 루트에서 사용하는 예시다. 현재는 스크립트가 없으므로 실행할 수 없다.

```powershell
# 기본 100명, 시드 42: 콘솔에 JSON 출력
python syntheticData/generatePersonas.py

# 인원과 시드 지정
python syntheticData/generatePersonas.py --count 100 --seed 42
```

생성기는 기본적으로 파일을 만들지 않는다. JSON 저장 기능을 추가한다면 `--output` 옵션을 명시한 경우에만 UTF-8 파일을 새로 만들고, 대상 파일이 이미 있으면 덮어쓰지 않고 실패하도록 제안한다.

```powershell
# 별도 결과 파일 생성까지 승인된 경우에만 사용
python syntheticData/generatePersonas.py --count 100 --seed 42 --output personas.json
```

초기 작업의 파일 수 제한을 지키기 위해 이 단계에서는 결과 파일을 생성하지 않는다. CSV가 필요하면 별도 승인 후 사용자·카테고리별 행으로 변환하는 방식을 검토한다.

## 8. 구현 후 검증 기준

- 기본 실행 결과의 사용자 수가 정확히 100명이다.
- ID와 이메일이 결과 내에서 중복되지 않고, 이름이 1~30자다.
- MBTI는 기존 16종, 카테고리는 기존 6종에만 속한다.
- 기본 100명에서 페르소나별 20명, MBTI별 6~7명이다.
- 사용자별 카테고리 점수는 모두 양의 정수이고 합계가 100이다.
- 선호 카테고리 2개가 최종 점수의 상위 2개와 일치한다.
- 같은 설정의 반복 실행 결과가 같고, 시드를 바꾸면 배정 또는 점수가 달라진다.
- 1명, 16명, 101명에서도 인원수와 분포 규칙을 만족한다.
- 0명, 음수, 정수가 아닌 인원은 명확한 오류와 실패 종료 코드로 처리한다.
- 출력 저장을 구현한다면 기존 파일 덮어쓰기 방지와 UTF-8 한글 보존을 확인한다.
- 검증 중에도 기존 파일 수정, DB 쓰기, 회원가입 요청이 발생하지 않는다.

## 9. 다음 승인 범위

문서 검토 후 승인받을 작업은 프로젝트 루트의 `../syntheticData/generatePersonas.py` 신규 작성과 파일 저장 없는 실행 검증이다. 문서와 생성 코드를 합쳐 신규 파일은 총 2개가 된다. 기존 파일 수정, 결과 파일 저장, DB·API 연동은 이 승인 범위에 포함하지 않는다.
