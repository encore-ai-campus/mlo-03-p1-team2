### 3.1. 콘서트 집중 재현 여부

전날 장애가 났던 같은 시나리오(같은 공연 `city`, 같은 곡선)를 다시 실행했지만 **장애는 재현되지 않았다.**
100 VU 구간에서도 모든 API p95가 87ms 이하였고, FastAPI CPU는 최대 19~21%였다. 이어서 실행한 야구 집중도 같았다.
따라서 전날 장애는 이 부하 자체로 생긴 것이 아닐 가능성이 크다. 전날 문서 7.2의 추정(같은 물리 호스트 문제나 수동 재시작)과 맞지만, 원인은 여전히 확인하지 못했다.

### 3.2. 조회 100 VU: 오늘 결과는 발생기 한계가 섞였다

| 지표 | 전날 | 오늘 |
| --- | ---: | ---: |
| 처리량 | 156.0 RPS | 112.3 RPS |
| 목록 p50 / p95 | 57 / 538ms | 412 / 583ms |
| 상세 p50 | 22ms | 175ms |
| FastAPI CPU 최대 (175 / 176) | 76% / 74% | **35% / 33%** |
| 발생기 프로세스 CPU (1코어 기준) | 평균 60%, 최대 97% | **중앙값 94%, 최대 100%** |

오늘은 서버 CPU가 전날의 절반인데 모든 API의 p50이 열 배쯤 높았다. 같은 시간에 부하 발생기 프로세스는 1코어를 거의 다 썼다.
즉 **오늘 조회 100 VU의 지연은 대부분 발생기(이 PC)의 처리 한계에서 생긴 것**이고, 서버의 한계를 보여주지 않는다.
조회 50 VU까지는 발생기 CPU 중앙값이 70% 이하라 결과를 믿을 수 있다.

조회 부하의 서버 쪽 한계는 전날 결과(100 VU에서 FastAPI CPU 76%, 목록 p95 538ms)와 같은 날 진행한 스트레스 시험(`docs/loadTestResult_claude_stress.md`, 조회·혼합 섞어 200 VU까지 기준 이탈 없음)으로 판단하는 편이 낫다.
조회 100 VU 이상을 정확히 재려면 발생기를 여러 프로세스나 여러 PC로 나눠야 한다.

## 6. 데이터 정합성

`verify_load.py` 결과 **통과**(오류 0건).

- 예매 3,785건 모두 결제와 짝이 맞는다. 상태 조합: `REQUESTED/PENDING` 2,497 · `CONFIRMED/COMPLETED` 1,278 · `CANCELLED/CANCELLED` 10.
- `(user_id, request_key)` 중복 0건. 201로 받은 예매는 모두 DB에 있고, 실행기가 모르는 예매는 없다.
- 행동 로그: 배치 15,644개, 수락 47,804건이 모두 1회씩 저장됐다(누락 0). 재전송한 100건은 서버가 중복으로 판단해 저장하지 않았다.

### 6.1. 정합성 전용 시험 (전날 미실행분)

| 시험 | 방법 | 데이터 결과 | 응답 코드 |
| --- | --- | --- | --- |
| 같은 키 동시 예매 | 10명 × 같은 `request_key`로 8건 동시 | **10개 키 모두 예매 1건만 생성** | 201 10 · 200 40 · **500 30** |
| 결제·취소 경합 | 10건 예매에 결제 3 + 취소 3 동시 | **10건 모두 최종 `CANCELLED/CANCELLED`, 상태 불일치 0** | 200 28 · 409 17 · **500 15** |
| 행동 로그 재전송 | 5배치 × 10건을 2번씩 동시 재전송 | 50건만 저장, 중복 0 | 모두 202 |

- **데이터는 지켜졌다.** 중복 예매 방지, 결제·취소 경합 후 상태 일치, 로그 중복 방지가 모두 동작했다.
- **하지만 동시 요청의 25~38%가 500을 받았다.** 정상이라면 같은 키 재요청은 기존 예매(200), 경합에서 진 요청은 409를 받아야 한다.
  DB 고유 제약 위반이나 잠금 충돌 예외를 FastAPI가 처리하지 못하고 그대로 500으로 내보내는 것으로 보인다. 서버 로그는 확인하지 못했다.
  사용자는 실제로 예매가 됐는데도 오류 화면을 보게 되고, 클라이언트가 재시도하면 혼란이 생길 수 있다. **백엔드 확인이 필요하다.**
- **후속 확인(같은 날):**
  - **같은 키 동시 예매의 500은 원인을 찾았고 수정했다.** `backend/app/api/routes/reservations.py`에서 고유 키 위반은 `db.flush()`에서 발생하는데, 예외 처리가 `commit()`만 감싸고 있었다. 그래서 flush부터 commit까지 함께 감싸도록 고쳤다.
    - 실제 MariaDB에서 재현했다: 8건 동시 요청 중 7건이 `IntegrityError 1062`.
    - 회귀 테스트 `test_request_key_race_returns_existing`, `test_request_key_concurrent_requests`를 추가했다.
    - 수정은 아직 배포되지 않았다.
  - **결제·취소 경합의 500은 MariaDB 데드락(1213)이었다.** 서버 로그로 확인했다(`docs/loadTestResult_claude_fixverify.md` 4.2절).
    - 처음에는 `Innodb_deadlocks` 카운터가 0이라 데드락이 아니라고 판단했지만, 틀렸다. 이 서버에서는 이 카운터가 데드락 발생을 반영하지 않는다.
- 같은 날 아침 첫 스트레스 시도(`loadtest-20261107-claude-stress`)에서 낮은 부하에도 쓰기 API 500이 났던 일과 같은 원인인지는 알 수 없다. 그때는 동시 요청이 아닌 일반 쓰기였다.

## 7. 결론

1. **혼합(실사용형) 부하 100 VU, 집중 100 VU, 30분 지속 100 VU를 모두 실패 0%로 견뎠다.** 이때 FastAPI CPU는 20% 안팎, MariaDB 연결은 151개 중 13개 이하로 여유가 컸다.
2. 전날 콘서트 집중 장애는 같은 부하로 재현되지 않았다. 부하 외 원인(호스트·수동 작업 등)을 확인해야 한다.
3. 조회 전용 100 VU는 두 번 다 목록 p95 기준(500ms)을 넘었다. 오늘은 발생기 포화가 주원인이라 서버 한계 측정으로 쓰기 어렵다. 서버 쪽 근거는 전날 결과(FastAPI CPU 76%)다.
4. 우선 조치 후보:
   - 동시 요청 시 500 응답 처리(같은 키 재요청은 200, 경합 패배는 409)
   - 인기순 목록의 `events` 전체 집계 개선(집계 테이블·캐시·인덱스). 데이터가 늘수록 비용이 커진다.
   - MariaDB exporter 복구(`mysql_up = 0`)

## 8. 미측정·한계

- 부하 발생기는 PC 1대·프로세스 1개다. 조회 100 VU에서 포화됐다.
- FastAPI·Nginx 로그, MariaDB slow log(OFF)는 보지 않았다. 500 응답의 실제 예외는 미확인이다.
- 조회 10 VU 구간의 서버 CPU 상승 원인은 미확인이다.
- MariaDB `information_schema` 크기는 통계 갱신 시점에 따라 실제와 다를 수 있다.
